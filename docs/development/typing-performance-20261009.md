# Typing performance — 3.3.24 / 20261009

> 当前交付状态（2026-09-15）：下列 A/B 测试针对 3.3.24；后续 3.3.25 / 20261010 的公开 APK 已在同一手机通过模式切换、快打、长按删除和生命周期复测，并原子发布到官网。手机已恢复同版本 private APK，原有内部配置保留。328 项 JVM 测试、46 项网页测试及静态检查通过。后续学习入口改动属于另一个 3.3.26 构建，不包含在已冻结的公开 APK 中。

本轮把日常安装版本从 `3.3.23 / 20261008` 升级到 `3.3.24 / 20261009`。在同一台手机、应用自有测试输入页上，以每秒 12 键输入 66 个合成拼音字母：旧版停止注入后的首次样本仍待处理 9–10 键，新版两轮首次样本均已处理完 66 键、队列为 0、预编辑拼写一致。后续开启纠错、开启云端以及 132 键扩展测试也通过同类检查。

这说明本轮测试中的长串输入积压明显减少；没有测得触摸到屏幕显示的端到端延迟，也不据此声明所有输入场景均无卡顿。

## 实现与构建

- Native Debug 构建启用 `-O2` 和 `NDEBUG`，减少未优化 native 路径对长句处理的影响。
- Rime 初始化设置 `min_log_level = 2`，减少常规日志开销。
- 调整协程上下文使用，减少逐键处理路径中的重复派发。
- 移除 routine 逐键日志，保留必要的异常诊断。
- JVM 回归测试：314 项通过。
- 固定签名证书已核验，`adb install -r` 覆盖安装成功；本轮没有卸载日常应用或清空其数据。

这些改动组合完成本次验证。现有记录不能分离量化每项改动的独立收益。

## 测量方法与指标口径

使用独立的 shell `app_process` 触摸注入工具，向已确认获得焦点的应用自有测试输入页发送真实屏幕 `MotionEvent` DOWN/UP。不安装第二个测试 APK。测试内容为合成输入，本记录仅保存长度、计数和统计值，不保存输入正文、凭据或私人文本。

逐键 DOWN 使用绝对时间计划，12 Hz 的目标间隔为 83.333 ms；单次接触持续 25 ms。66 键对应 132 个触摸事件，注入约 5.442 秒。基础 A/B 五轮均接受全部 132 个触摸事件，DOWN 平均间隔约 83.333–83.337 ms。通过注入过程之外的计数器采样核对已处理键数、待处理队列和预编辑拼写。

- “首次停止后样本”是注入结束后首次取得的外部样本，不是触摸 UP 时刻的同步快照。
- “已处理键数”使用 `processedKeyCount` 相对该轮 `before` 的增量；待处理数使用 `queueDepth`。
- `maximum*` 字段是进程内累计高水位。若该轮刷新高水位，可确认该轮的新最大值；若没有刷新，只能给出该轮上界，不能把旧值认定为本轮实际峰值。
- 下文“处理最大值”对应 `maximumNativeProcessingMicros`。它是现有服务处理计时指标，不等于隔离测量的纯 native 计算耗时，也不包含完整屏幕显示路径。
- `polledDrainMs` 受外部采样、轮询和命令边界影响，不是端到端延迟。新版的 0–4 ms 不能称作“打字延迟为 0–4 ms”。
- 新版 `maximumQueueWaitMicros = 2410754` 在首轮输入前已存在，包含约 2.411 秒冷启动等待；下列新版测试未刷新该值，不能用它表示逐键输入等待峰值。
- `discardedPresentationSnapshots` 统计被替代的展示快照，不能解释为输入键丢失。

## 66 字母、12 Hz 的 A/B 结果

表中所有计数均来自各轮自己的起始样本；“最后样本”指记录中名为 `settled` 的样本，名称本身不保证队列已排空。

| 报告标签 | 首次停止后：已处理 / 待处理 | 最后样本 | 本轮队列峰值 | 本轮处理最大值 |
| --- | ---: | --- | ---: | ---: |
| baseline (`long-12-hz`) | 56 / 10 | 61 / 5，尚未排空 | 16 | 436.746 ms，限已记录阶段 |
| correction-off | 57 / 9 | 66 / 0，拼写一致 | ≤16 | 472.650 ms |
| profile-off | 56 / 10 | 66 / 0，拼写一致 | ≤16 | 527.139 ms |
| optimized-off | 66 / 0 | 66 / 0，拼写一致 | 3 | 88.848 ms |
| optimized-off-repeat | 66 / 0 | 66 / 0，拼写一致 | ≤3 | ≤88.848 ms |

baseline 的最后样本只处理 61 键，预编辑也恰好含 61 个拼音字母，另有 5 键仍在队列中。因此该记录的 `exactSpelling = false` 只能证明采样时未完成，不能据此认定丢键，也不能给出这一轮最终排空耗时或完整处理峰值。

correction-off 和 profile-off 的轮询排空记录分别为 2746 ms、2383 ms；新版两轮均为 4 ms。结合首次样本中的待处理数，可以确认旧版停止注入后仍有积压，而新版首次样本已经排空；不能直接把这些轮询值相减作为端到端延迟改善量。

队列累计高水位在 baseline 由 3 升至 16，在新版首轮由 2 升至 3，因此这两轮的峰值可确定。其余三轮没有刷新各自的累计高水位，表中用上界表示。展示快照丢弃增量按表格顺序分别为 8、14、12、1、0；所有记录中的过期候选选择计数均为 0。

不能把改进解释为所有阶段都更快：旧会话展示构建累计高水位为 15.866 ms，新版首轮记录到 44.378 ms。新版的 88.848 ms 处理最大值也略高于 12 Hz 的单键间隔。现有样本没有提供逐键处理分布或帧时间，不能推出每键都满足某个显示时延阈值。
